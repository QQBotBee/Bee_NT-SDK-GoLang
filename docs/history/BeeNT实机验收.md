# BeeNT Go 1.0.1 实机操作记录（历史）

本文件保存此前已完成的实机测试步骤，仅供 SDK 维护追溯。当前日常开发仅运行根目录 build.bat 构建自己的插件，再导入真实 BeeNT 验证功能。原测试业务已归入 other/tests/fixtures/acceptance，不提供独立验收构建入口。

当时实测插件名为 **BeeNT Go 验收插件**，版本 **1.0.1**，实机环境为 Windows Server 2012 R2。该业务已归档为内部测试 fixture，本文保留原操作步骤。

当时针对 Worker 启动和旧系统兼容性进行了检查。当前构建的版本、资源与 PE 核验在内部完成，只交付 DLL；原生壳仅导入 KERNEL32.dll，不依赖 UCRT。

**验收状态：2026-11-05，用户确认下表 16 项测试全部通过（16/16）。** 实机环境为此前确认的 Windows Server 2012 R2，实测版本为 1.0.1。用户先确认 `ping` 和设置窗口恢复正常，随后完成全部 16 项验收。工具链与入口随后统一为 Go 1.20.14；本地回归与历史实测依据见 [验证记录](../验证记录.md)。

## 准备

1. 先禁用旧插件并退出 BeeNT，替换为对应系统的 `1.0.1` DLL 后重新启动，确认名称和版本正确再启用。避免同名插件重复加载。若卸载会删除数据目录，先保存日志。
2. 用另一个 QQ 账号给机器人发消息。群聊测试使用机器人和测试账号都在的测试群；机器人自己的消息会被忽略。
3. 所有指令都必须以 `/beent` 开头，私聊和群聊分别测试。普通消息不会自动回复。
4. 运行文件与日志位于 `<BeeNT宿主EXE所在目录>\plugin_data\BeeNT Go 验收插件\`。目录由运行时创建；不要把 SDK 工程中的 `build` 目录当成真实客户端数据目录。

## 建议按顺序操作

| 步骤 | 操作 | 预期结果 |
| --- | --- | --- |
| 1. 加载与启用 | 导入 DLL，启用插件 | 管理页显示正确名称/版本；框架不崩溃、不长时间卡住，数据目录中生成 `acceptance.log` |
| 2. 私聊收发 | 测试账号私聊机器人发送 `/beent ping` | 在这个私聊收到 `PONG`，没有重复回复 |
| 3. 群聊收发 | 在测试群发送 `/beent ping` | 回复 `PONG` 到原群，私聊不会收到这条群回复 |
| 4. 中文与 emoji | 发送 `/beent echo 中文 ABC 123 😀`，再发送包含换行的 echo | 回复保留中文、英文、数字、emoji 和换行；不要显示成乱码、问号或字面 `\uXXXX` |
| 5. 框架信息 | 发送 `/beent info` | 显示框架名、版本、机器人 QQ 及机器人信息；QQ 与当前登录账号一致 |
| 6. 回调参数 | 私聊和群里分别发送 `/beent id` | 场景、来源 ID、发送者 ID、消息 ID 正确；群聊来源应为群号，发送者应为测试账号，消息 ID 可以是负数 |
| 7. 引用回复 | 发送 `/beent quote` | 客户端出现真正的引用回复，引用这条测试账号发出的指令 |
| 8. 撤回 | 先 `/beent ping`，看到 `PONG` 后立即 `/beent recall` | 插件撤回刚才自己发送的 `PONG`；测试账号发出的指令仍保留。私聊和群聊各测试一次 |
| 9. 后台 API | 发送 `/beent bg 后台中文😀` | 指令返回后约 2 秒，在原会话收到 `后台中文😀`，用于验证回调之外调用框架 API |
| 10. 本地持久化 | 连续发送两次 `/beent data`；禁用再启用或重载，再发送一次 | 计数连续增加，重载后继续递增，`acceptance_state.json` 内容与回复一致 |
| 11. 事件参数 | 在希望收到结果的会话发送 `/beent event on`，再在测试群修改自己群名片或戳一戳机器人 | 该会话收到事件摘要，类型、来源、触发者和操作者与操作对应；日志保留八个事件原始字段。某些事件字段为空取决于框架 |
| 12. 停止事件通知 | 在同一会话发送 `/beent event off`，再触发上述事件 | 该会话不再收到事件推送；日志仍记录框架传入的事件 |
| 13. 设置窗口 | 打开插件设置，重复点击设置，关闭后再打开 | 同时只有一个窗口，重复点击可聚焦；窗口文字正常，关闭后可重新打开 |
| 14. 禁用清理 | 发送 `/beent bg 不应出现` 后立即禁用；也测试打开设置后立即禁用 | 待执行的延迟回复取消，设置窗口关闭，Worker 进程退出，宿主不挂起；禁用要在约 2 秒延迟到期之前完成 |
| 15. 重复重载 | 启用→ping→禁用，以及重载→ping，各重复数次，建议共 10 轮 | 每次均只回复一次，能够继续调用 API；没有僵死窗口、持续累积的 Worker 或加载失败 |
| 16. 卸载/退出 | 最后卸载插件，或正常退出 BeeNT | 没有残留设置窗口和本插件的 Worker 进程；框架卸载操作可能删除插件数据目录，先保存验收日志 |

换行测试应作为一条消息发送，例如：

```text
/beent echo 第一行 中文😀
第二行 ABC 123
```

预期回复为：

```text
第一行 中文😀
第二行 ABC 123
```

私聊与群聊的发送、引用、撤回接口不同，步骤 2–9 应尽量在两种场景各做一次。撤回需要框架实际发送接口返回有效的数值消息 ID；如果返回的是错误文本，验收插件会记录原文并拒绝拿它当消息 ID。回复“请求已提交”本身不能证明 QQ 服务器已完成撤回，应以客户端消息消失为准。

事件通知只会发送到执行 `event on` 的会话，订阅在禁用/重载后清空。可用群名片变动（类型 `28`）或戳一戳（类型 `23`）验证；是否产生该回调仍由 BeeNT 的实际事件接收能力决定。无需为了测试加入群、禁言或踢人。

可选：若有现成的后置观察插件，可把验收插件排在其前面，对比普通 `ping` 与 `/beent intercept`。只有 `intercept` 返回拦截值 `1`，应阻止排在后面的插件收到该条指令；其它验收指令返回 `0`。没有观察插件时可跳过，这个步骤的原生返回值会在本地模拟宿主检查。

## 日志与结果反馈

数据目录包含以下诊断文件：

- `bridge.log`：原生壳记录设置调用、Worker 启动、启动失败阶段/Win32 错误码、异常退出码和回调错误。Worker 尚未运行时也能写入；数据目录不可写时回退到 `%TEMP%\beent-bridge-<BeeNT进程ID>.log`。
- `worker-stderr.log`：专用捕获 Worker 的启动错误、Go runtime 错误及标准错误输出，不依赖 GUI 宿主是否提供控制台。
- `acceptance.log`：UTF-8 JSON Lines，每行一个记录，包含生命周期、实际 Go 版本、验收消息、事件八参以及框架 API 的请求和返回原文。
- `acceptance_state.json`：持久化计数。

Worker 可在任务管理器的“详细信息”页按 `beent_go_worker` 文件名前缀查找；文件名还含宿主 PID 等标识，可结合路径区分其它插件。

后续修改 SDK、插件业务或运行环境时，可复用上述 16 项进行回归。若出现问题，请提供失败步骤、实际回复/报错、BeeNT 版本，以及 `bridge.log`、`worker-stderr.log` 和存在时的 `acceptance.log`。日志含 QQ/群号、消息文本和事件字段，分享前可替换为一致的占位值，保留字段名、操作码、参数顺序和错误原文。
