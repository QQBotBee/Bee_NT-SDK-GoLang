## 初始实现记录（历史）

日期：2026-11-05（Asia/Shanghai）。本地工具为 Go 1.27.3 windows/amd64、Zig 0.17.0；模块声明 Go 1.22，未引入高于 Go 1.22 的标准库 API。

## 通过

- amd64：`go test -count=1 ./...`、`go vet ./...`。
- 386：设置 `GOARCH=386` 后同上两条命令；测试在本机实际执行，不仅编译。
- 格式：`gofmt -l .` 无输出。
- `cmd /c build.bat --no-pause` 生成单个最终 DLL。
- `other/tests/run.ps1`：实际 x86 LoadLibrary；元数据、七个函数指针、stdcall 回调、中文 GBK 往返、回调之外的后台 API、三轮重载；核心 API 阻塞时保留 DLL 生命周期；Worker 停读超时；两个并发消息回调期间禁用或卸载后立即 FreeLibrary。
- `other/tests/run-go-host.ps1`：最终 DLL 内嵌实际生产 Go Worker，完成三轮 initialize/enable/API/好友/群聊/八参事件/disable/uninstall/reload。
- SDK 单元测试逐项验证全部 97 个具名 API 的编号与业务参数顺序，typed 结构、列表和 Unicode 边界。
- 独立审阅对照了接收端 97 项接口、Windows 窗口布局、Worker 并发及 C 生命周期；实质发现已修复并验证。

## 未验证范围

`go test -race ./...` 在默认 `CGO_ENABLED=0` 环境不能运行。临时启用 CGO，使用 Zig 并链接 `api-ms-win-core-synch-l1-2-0` 后，race 检测器启动时报 `ThreadSanitizer failed to allocate ... (error code: 87)`。没有得到 race 检测通过结论，未修改全局 Go 环境设置。

本目录没有真实 BeeNT 客户端及测试账号；实际框架中的 API 网络返回、消息投递、设置窗口交互和长时间重复重载需要实机验收。模拟核心使用 stdcall 单文本输入、文本指针输出；C 壳复制返回内容、不释放框架拥有的指针。宿主须持有 DLL 至禁用/卸载返回，并停止继续调用旧函数地址。异常回调无法及时排空时宁可保留模块引用，避免执行已释放的代码。

## 1.0.1：Server 2012 R2 启动兼容性修正

2026-11-05 用户实机反馈：Server 2012 R2 上点击设置无反应，`/beent ping` 也没有回复。复核旧 `1.0.0` 产物实际内嵌 Go 1.27.3 Worker，PE OS/subsystem 为 10.0，C 壳导入 UCRT。此前 `go.mod` 的 `go 1.22` 没有限制构建实际使用的编译器。

本机旧 DLL 的真实设置回调能创建窗口，因此没有更改窗口绘制业务。修正聚焦于 Worker 启动环境：默认工具链精确锁定 Go 1.22.12；旧系统另用 Go 1.20.14；最低语言声明改 Go 1.20。Go 1.21 起官方最低 Windows 10 / Server 2016，Go 1.22 不能当作 Server 2012 R2 的官方支持版本。

原生壳改为无 CRT 构建，只导入 KERNEL32.dll；保留正确的 x86 逐页栈探测。最终 DLL 资源中的 Worker 会被提取，核验实际 Go buildinfo、x86 PE32、哈希以及旧系统产物 OS/subsystem ≤6.3，记录于同名 `.build.json`。新增 `bridge.log` 与 `worker-stderr.log`，覆盖 Worker 尚未启动的失败。

本轮验证：

- Go 1.20.14 与 Go 1.22.12：SDK 的测试/vet，以及验收业务的 amd64/386 测试/vet 通过。旧版 vet 不支持 overlay 虚拟新增测试文件，验收测试脚本改为同源的隔离物理包。
- 两份最终 DLL 的 `run-settings-host.ps1` 均通过：未启用直接设置、真实可见 HWND、单实例、WM_CLOSE、重开及禁用销毁。
- 两份最终 DLL 的 `run-acceptance-host.ps1` 均通过两轮：私群回复、编码、引用、只撤回最新自发消息、信息/ID、后台 API、取消和重载。
- `run.ps1` 五组原生边界测试在无 CRT 壳下再次通过。
- `run-diagnostic-host.ps1` 三组通过：GUI 宿主无 stderr 仍捕获 Worker 输出/退出 42、记录设置回调错误、记录无效 Worker 的 CreateProcess 错误 193/216。
- `run-crt-probe.ps1` 通过：格式/编码/截断、内存重叠和真实新线程 guard 页扩栈；独立审阅未发现阻断问题。
- `test-build-toolchain.ps1` 拒绝错误编译器、架构、CGO、外部 CRT/非系统导入、过高 PE 版本；两种工具链的 overlay 构建与实际 Worker 回归通过。
- 根代理重新提取两份交付 DLL 的资源，独立复核实际 Go 版本、PE、导入表与哈希；本地测试结束后检查 Worker 无残留。

2026-11-05，用户在此前确认的 Server 2012 R2 环境复测后反馈：“这次可以了，可以收到 `/beent ping` 的响应，也可以打开设置菜单。”据此确认本次实机的 Worker 启动、`ping` 消息收发和设置菜单打开已通过。
